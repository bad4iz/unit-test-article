# Первый тест должен быть тупым. Умничать будете во втором

> Рабочий черновик. Полный текст ведётся в репозитории; [на Хабре](https://habr.com/ru/articles/1098522/) только заголовок и пометка о доработке. Вопросы перед публикацией — в [редакторских заметках](notes/07_first_test_smoke.md).

Открываешь новый тестовый файл, замокал зависимости, написал сценарий — красное. Теперь надо понять, что именно не так. Функция считает неправильно? Мок вернул не ту структуру? Или до расчёта вообще не дошли, потому что зависимость попыталась достать данные из отсутствующего контекста?

Поэтому первый `it` у меня обычно скучный. Задаю обычные моки, вызываю код и убеждаюсь, что он хотя бы запустился. Без проверки каждого поля, вызова обработчиков и снимка на полэкрана. До них ещё доберёмся.

Я начинаю такой файл с `it('🧪 default')`: внутри `mockDefault()`, вызов setup-хука и `expect(result).toBeDefined()`. Следом идут отдельные тесты структуры результата и конкретного поведения. Покажу этот приём на небольшой панели профиля.

## Что делает первый тест

Вот первый тест из учебного примера к статье:

```javascript
it('🧪 smoke: выполняется с обычным ответом зависимости', () => {
  expect.hasAssertions();

  //☣️ Arrange
  mockDefault();

  //🔥 Act
  const result = useSetupProfilePanel();

  //❓ Assert
  expect(result).toBeDefined();
});
```

Его задача — подтвердить, что с базовой подготовкой можно вызвать setup-хук и получить результат. Какое имя попадёт в карточку и что будет во время загрузки, этот тест не выясняет.

Это и есть мой smoke-тест на уровне одного модуля: завелось — можно разбирать сценарии. В нём почти нечего проверять, но действие настоящее: модуль загружен, зависимости подготовлены, код вызван. В статье вместо короткого `default` я написал назначение прямо в имени теста.

## Что здесь замокано

Возьмём небольшую панель профиля. Setup-хук получает состояние профиля и готовит данные для компонента:

```javascript
import { useProfile } from './useProfile';

export function useSetupProfilePanel() {
  const state = useProfile();

  if (state.status === 'loading') {
    return { isLoading: true, userCardProps: null };
  }

  return {
    isLoading: false,
    userCardProps: { name: state.profile.name },
  };
}
```

Для изолированной проверки подменяю `useProfile`. Сам `useSetupProfilePanel` остаётся настоящим — иначе запустить было бы нечего.

```javascript
import { describe, expect, it, vi } from 'vitest';

import { useProfile } from './useProfile';
import { useSetupProfilePanel } from './useSetupProfilePanel';

vi.mock('./useProfile');

/**
 * Задаёт готовый профиль; нужные отклонения задаём в Arrange конкретного теста.
 *
 * @returns {void}
 */
const mockDefault = () => {
  useProfile.mockReturnValue({
    status: 'ready',
    profile: { id: 'profile-1', name: 'имя по умолчанию' },
  });
};
```

Это начало [тестового файла](examples/first-test-smoke/src/useSetupProfilePanel.test.js); первый `it` из предыдущего блока находится в его `describe`.

В `mockDefault()` лежит один согласованный сценарий. Если состояние `ready`, в нём есть профиль. При подготовке такого теста проще заметить, что забыл поле или вообще не настроил ответ мока. Не приходится одновременно разбираться ещё и с ожидаемым именем, состоянием загрузки и содержимым карточки.

Здесь setup-хук можно вызвать напрямую: `useProfile` замокан, а в самом `useSetupProfilePanel` нет прямых вызовов React-хуков. Если там появится настоящий `useState` или `useContext`, потребуется запуск через React, например `renderHook`. Название smoke не отменяет [правила вызова хуков](https://react.dev/warnings/invalid-hook-call-warning).

## А потом уже проверяем результат

Второй тест начинается с той же подготовки, но меняет данные под конкретный сценарий:

```javascript
it('🧪 готовит имя для карточки из полученного профиля', () => {
  expect.hasAssertions();

  //☣️ Arrange
  mockDefault();
  useProfile.mockReturnValue({
    status: 'ready',
    profile: { id: 'profile-42', name: 'другое имя' },
  });

  //🔥 Act
  const result = useSetupProfilePanel();

  //❓ Assert
  expect(result).toEqual({
    isLoading: false,
    userCardProps: { name: 'другое имя' },
  });
});
```

Тут уже есть конкретное требование: имя должно прийти из профиля. Отдельный тест проверяет состояние загрузки. У каждого понятна причина существования.

Чтобы увидеть разницу, достаточно временно захардкодить в реализации `name: 'чужое имя'`. Первый тест останется зелёным: объект вернулся, выполнение не сломалось. Проверка имени упадёт. Именно такой эксперимент сделан для примера к статье.

## Что означает красный первый it

Если забыть `mockDefault()`, замоканный `useProfile` в нашем примере вернёт `undefined`. Обращение к `state.status` упадёт. Причина действительно в подготовке теста, и строгая проверка имени сейчас ничего полезного не добавит: до неё код не добрался.

Но тот же первый `it` упадёт, если в самом setup-хуке обратиться к несуществующему свойству или бросить исключение. Поэтому по одному красному индикатору нельзя объявить виновными исключительно моки. Тест выполняет настоящий код — настоящий косяк тоже попадёт в него.

Я использую результат так:

| Что вижу | С чего начинаю разбор |
| --- | --- |
| Упал минимальный запуск | Смотрю исключение и стек: ответ зависимости, обязательные данные, контекст, код инициализации |
| Минимальный запуск зелёный, один сценарий красный | Смотрю отличия этого сценария: переопределение мока, входные данные и ожидаемый результат |
| Вместо результатов тестов ошибка загрузки файла | Разбираюсь с импортами, конфигурацией и подготовкой модулей: до первого `it` могли вообще не дойти |
| По одному всё зелёное, вместе падает | Ищу утечку состояния, неочищенные моки и зависимость от другого теста |

Сначала смотрю на этот короткий запуск. Не приходится разбирать огромный snapshot, когда у мока просто забыли настроить возврат.

## Для компонента — такой же короткий запуск

Компонент панели получает данные из setup-хука. В его тестах мокается уже этот хук, а сборку элементов выполняет настоящий `ProfilePanel`:

```javascript
import { shallow } from 'shallowly';
import { describe, expect, it, vi } from 'vitest';

import { ProfilePanel } from './ProfilePanel';
import { useSetupProfilePanel } from './useSetupProfilePanel';

vi.mock('./useSetupProfilePanel');

/**
 * Готовит обычный ответ setup-хука для изолированной проверки разметки.
 *
 * @returns {void}
 */
const mockDefault = () => {
  useSetupProfilePanel.mockReturnValue({
    isLoading: false,
    userCardProps: { name: 'имя по умолчанию' },
  });
};

describe('🐛 spec ProfilePanel', () => {
  it('🧪 smoke: собирает разметку без исключения', () => {
    expect.hasAssertions();

    //☣️ Arrange
    mockDefault();

    //🔥 Act
    const renderPanel = () => shallow(<ProfilePanel />);

    //❓ Assert
    expect(renderPanel).not.toThrow();
  });
});
```

В `Act` подготовлен вызов. Сам запуск происходит внутри `not.toThrow()`: matcher получает функцию и проверяет отсутствие синхронного исключения. [Документация Vitest](https://v4.vitest.dev/api/expect#tothrow).

Дальше отдельно проверяю заголовок, данные карточки и ветку загрузки. Обработчики дочерних компонентов в этом shallow-тесте не вызываю. Shallowly собирает дерево элементов без DOM и без исполнения дочернего `UserCard`; зелёный результат относится именно к этому запуску. Как всё работает вместе в браузере — другой вопрос и другие проверки.

## Несколько деталей, которые стоит учесть

Пустой `it` не вызывает нужный код. `expect(true).toBe(true)` тоже ничего не говорит о его работоспособности. В моём первом тесте важно само действие: вызываем реальный модуль с подготовленными зависимостями.

С matcher тоже не надо гадать. [`toBeDefined()`](https://v4.vitest.dev/api/expect#tobedefined) проверяет только отличие от `undefined`. `null` и пустой объект через него пройдут. Для функции, которая по контракту вообще ничего не возвращает, такая проверка будет неверной — ей подходит синхронный `not.toThrow()`, как выше.

`expect.hasAssertions()` оставляю по принятому в проекте шаблону: он требует выполнить хотя бы одну assertion. [Документация Vitest](https://v4.vitest.dev/api/expect#expect-hasassertions).

Для асинхронной функции надо дождаться завершения. Если она возвращает результат, схема остаётся той же:

```javascript
// Фрагмент внутри async-теста: loadProfile возвращает Promise с профилем.
const result = await loadProfile();
expect(result).toBeDefined();
```

Если обещанный результат — `Promise<void>`, проверка успешного завершения выглядит как `await expect(saveProfile()).resolves.toBeUndefined()`. Оборачивать асинхронный вызов в обычный `not.toThrow()` недостаточно: так можно пропустить отказ Promise. [Асинхронные проверки Vitest](https://v4.vitest.dev/api/expect#resolves).

## Первый — не значит «подготовительный для остальных»

Я ставлю smoke первым, чтобы с него было удобно начать написание и чтение файла. Другие тесты от него не зависят. Каждый сам вызывает `mockDefault()` и задаёт условия своего сценария. Любой из них должен запускаться отдельно.

Если первый `it` настроил моки, а второй пользуется оставленным состоянием, это уже сломанная изоляция. Перенос подготовки из `beforeEach` в первый тест ничего не исправляет. В Vitest существуют и параллельный запуск, и перемешивание порядка; рассчитывать на первого соседа вообще незачем. [Настройки порядка запуска](https://v4.vitest.dev/config/sequence#sequence-shuffle).

В учебном примере служебный сброс настроен в Vitest:

```javascript
test: {
  mockReset: true,
  restoreMocks: true,
}
```

После сброса `mockDefault()` заново задаёт обычные ответы. `mockReset` здесь важен: очистить только историю вызовов — не то же самое, что сбросить реализации и очередь разовых ответов. Подробности подготовки вынесены в [отдельный черновик про mockDefault](https://github.com/bad4iz/unit-test-article/blob/docs/mock-default-test-setup/05_mock_default.md). [Настройки Vitest](https://v4.vitest.dev/config/mockreset).

## Оставлять ли его в готовом наборе

Мне такой первый тест удобен в модуле, где есть что настраивать: несколько зависимостей, контекст, setup-хук. Открыл файл — сразу видно минимальный рабочий запуск. Из него уже можно взять основу для следующего сценария.

Строгое сравнение всей структуры или snapshot уже фиксируют конкретный результат. В первый smoke я их не тащу.

Если у простой функции первый содержательный тест и так состоит из одного вызова и сравнения числа, отдельный smoke может ничего не добавить. Моё соглашение помогает разбирать сложную подготовку; создавать лишний `it` ради количества мне неинтересно.

И заканчивать набор на smoke нельзя. Он может выполнить много строк и приятно поднять coverage, но подмену имени мы уже видели: код прошёл, ошибка осталась. После «завелось» нужны проверки того, ради чего этот код написан.

## Запустить пример

В [examples/first-test-smoke](examples/first-test-smoke) лежат компонент, setup-хук и шесть тестов. Нужен Node.js 22.12+ из ветки 22 либо Node.js 24.

```bash
git clone --branch docs/first-test-smoke https://github.com/bad4iz/unit-test-article.git
cd unit-test-article/examples/first-test-smoke
npm ci
npm test
```

Два теста проверяют минимальный запуск, остальные четыре — конкретные результаты. В README описан эксперимент с подменой имени: можно повторить и посмотреть, какая проверка её заметит.
