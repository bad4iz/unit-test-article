# React Testing Library — не для юнит-тестов. А что тогда использовать?

![Разработчик пытается проверить одну панель, окружённую дочерними компонентами и моками](assets/shallowly-vs-rtl/cover-body.jpg)

Мне нужен тест одного компонента. Открываю файл: небольшой кусок JSX, несколько детей, данные из хука. Вроде ничего сложного. Запускаю тест — одному ребёнку нужен провайдер. Разобрался с ним — у другого обнаружилась зависимость, о которой по коду родителя вообще не догадаешься. Начинаешь замокивать всё это по очереди.

Тест ещё толком не написан, а окружение для него уже собираешь.

Вот это меня и напрягает в React Testing Library, когда я использую её для изолированной проверки компонента. Мало написать моки. Их потом надо поддерживать, а при падении выяснять, что сломалось: мой компонент, его ребёнок, их взаимодействие или сама заглушка. И время выполнения всего этого хозяйства тоже имеет значение.

Я автор [Shallowly](https://www.npmjs.com/package/shallowly). Покажу задачу, для которой выбираю её, на одном небольшом примере. Оба варианта теста можно запустить.

## Почему вообще появляются эти моки

React Testing Library рендерит компонент через React в DOM. В тестах ниже это DOM из jsdom, без запуска браузера. Если панель возвращает карточку пользователя, React вызовет и карточку. Если внутри карточки есть ещё компоненты и хуки, очередь дойдёт и до них — если они участвуют в текущем рендере.

В [документации RTL](https://testing-library.com/docs/react-testing-library/intro/) этот подход описан прямо: работа с DOM и проверки, близкие к использованию интерфейса. От [shallow-рендера RTL отказывается сознательно](https://testing-library.com/docs/react-testing-library/faq/).

Для проверки собранного интерфейса такое поведение мне подходит. Но сейчас задача уже: проверить, что конкретная панель правильно собирает свои элементы. Лезть в реализацию каждого ребёнка ради этого я не хочу.

Можно оставить детей настоящими и подключить нужные провайдеры. Можно подменить сервисы, с которыми они работают. А можно замокать самих детей. Последний вариант даёт нужную мне границу проверки, но эту границу приходится расставлять руками.

Причём по импортам родителя не всегда видно, сколько работы впереди. Название `UserCard` ничего не говорит о том, что глубже понадобится локаль, роутер или клиент запросов. Иногда выясняешь это итеративно: запустил, получил ошибку, нашёл зависимость, подменил, запустил ещё раз. Хочется уже добраться до самой проверки.

Это не требование RTL «мокать всё». Это цена выбранной мной изоляции при использовании инструмента, который рендерит дерево.

## Возьмём панель профиля

Входных пропсов у панели нет. Подготовку данных держу в `useSetupProfilePanel`, в компоненте оставляю разметку. Соглашение `useSetup[Component]` использую, чтобы по имени было понятно, для какого компонента собрана логика.

```javascript
import { ActivityFeed } from './ActivityFeed';
import { UserCard } from './UserCard';
import { useSetupProfilePanel } from './useSetupProfilePanel';

export function ProfilePanel() {
  const { isLoading, userCardProps, activityFeedProps } = useSetupProfilePanel();

  if (isLoading) {
    return <p role="status">Loading profile...</p>;
  }

  return (
    <section aria-label="Profile">
      <h1>Your profile</h1>
      <UserCard {...userCardProps} />
      <ActivityFeed {...activityFeedProps} />
    </section>
  );
}
```

У панели две ветки: сообщение о загрузке и готовый профиль. В готовом состоянии есть заголовок, карточка и лента активности.

В полном примере `UserCard` читает локаль из контекста, а `ActivityFeed` — сервис, который возвращает активность профиля, из другого контекста. Это небольшие учебные зависимости, без запросов к бэку. Их достаточно, чтобы показать, почему простой `render(<ProfilePanel />)` с настоящими детьми требует окружения.

Для теста самой панели задаём готовый ответ setup-хука. Как он получил данные, здесь не проверяем. Нас интересует, какие элементы панель вернула и что в них положила. Обработчики из shallow-теста тоже не вызываем: их логика относится к хуку.

## Сначала через React Testing Library

Замокаем setup-хук и обоих детей. Не будем писать для заглушек собственные кнопки, карточки и обработчики: для этой проверки им достаточно возвращать `null`.

```javascript
// @vitest-environment jsdom

import { render } from '@testing-library/react/pure';
import { describe, expect, it, vi } from 'vitest';

import { ActivityFeed } from './ActivityFeed';
import { ProfilePanel } from './ProfilePanel';
import { UserCard } from './UserCard';
import { useSetupProfilePanel } from './useSetupProfilePanel';

vi.mock('./useSetupProfilePanel');
vi.mock('./UserCard');
vi.mock('./ActivityFeed');

/**
 * Задаёт обычный ответ setup-хука и пустую разметку дочерних компонентов.
 *
 * @returns {void}
 */
const mockDefault = () => {
  useSetupProfilePanel.mockReturnValue({
    isLoading: false,
    userCardProps: { name: 'имя по умолчанию' },
    activityFeedProps: { profileId: 'default-profile' },
  });
  UserCard.mockReturnValue(null);
  ActivityFeed.mockReturnValue(null);
};

describe('🐛 spec ProfilePanel: React Testing Library, изоляция', () => {
  it('🧪 собирает карточку и ленту с данными setup-хука', () => {
    expect.hasAssertions();

    //☣️ Arrange
    mockDefault();
    const userCardProps = { name: 'имя из хука' };
    const activityFeedProps = { profileId: 'profile-42' };
    useSetupProfilePanel.mockReturnValue({
      isLoading: false,
      userCardProps,
      activityFeedProps,
    });

    //🔥 Act
    render(<ProfilePanel />);

    //❓ Assert
    expect(UserCard.mock.calls.at(-1)?.[0]).toEqual(userCardProps);
    expect(ActivityFeed.mock.calls.at(-1)?.[0]).toEqual(activityFeedProps);
  });
});
```

Здесь я намеренно сделал моки короткими. Vitest [умеет автоматически подменять экспорты модуля](https://vitest.dev/api/vi.html#vi-mock), поэтому фабрики с ручным `vi.fn()` для каждого ребёнка не нужны. Названия детей всё равно перечислены отдельно: `UserCard`, `ActivityFeed`.

В `mockDefault()` задаю обычный сценарий, а его вызов оставляю прямо в начале теста. Подготовку не прячу в `beforeEach`: хочу читать условия вместе с проверкой. Сброс моков и очистка DOM настроены один раз для всего примера.

После рендера смотрю на первый аргумент последнего вызова каждого замоканного ребёнка. Это переданные ему пропсы. Число вызовов здесь не проверяю: к задаче панели оно не относится.

Важный момент: я уже вышел за обычную для RTL проверку видимого интерфейса. Мне нужны границы компонентов, поэтому наблюдаю вызовы моков. RTL это не запрещает, просто получить такой тест одной командой `render` не выходит.

## Написать заглушку — половина дела

В примере два ребёнка, и весь список перед глазами. Добавим в панель ещё блок — для такой же изоляции придётся добавить и его мок. Оставим его настоящим — в проверке начнут участвовать его реализация и зависимости.

Хуже становится, если заглушки изображают часть поведения: возвращают разметку, принимают ввод, вызывают обработчики. У настоящего компонента меняется интерфейс или смысл работы, а мок продолжает жить по старым правилам. Типы могут подсказать, что переименован или удалён пропс. Проверить, что заглушка по-прежнему ведёт себя как настоящий компонент, одних типов недостаточно.

У моков, возвращающих `null`, этой проблемы меньше: они не притворяются работающей карточкой. Но список детей, которых надо заглушить, всё равно поддерживаю руками. Импорты компонентов и ожидаемые данные нужны в обоих вариантах теста; дополнительная работа здесь — именно подмены.

![Разработчик ищет причину красного теста между компонентом, его ребёнком и моком](assets/shallowly-vs-rtl/debugging-body.jpg)

При падении приходится разбираться, какой именно вариант перед нами. Родитель передал не те данные? Настоящий ребёнок теперь требует новое окружение? Заглушка изображает поведение, которого уже нет? Или ожидание в тесте само по себе ошибочное?

Стек ошибки иногда сразу отвечает на этот вопрос. Иногда показывает место, где всё упало, а почему туда вообще дошло выполнение — ещё надо раскрутить. Вот этот дебаг мне особенно не нравится: хотел локальную проверку, а разбираю окружение нескольких компонентов.

## Тот же тест через Shallowly

Оставим те же данные и то же требование к панели. Уберём моки детей.

```javascript
import { shallow } from 'shallowly';
import { describe, expect, it, vi } from 'vitest';

import { ActivityFeed } from './ActivityFeed';
import { ProfilePanel } from './ProfilePanel';
import { UserCard } from './UserCard';
import { useSetupProfilePanel } from './useSetupProfilePanel';

vi.mock('./useSetupProfilePanel');

/**
 * Задаёт обычный ответ setup-хука; особые состояния меняем в самом тесте.
 *
 * @returns {void}
 */
const mockDefault = () => {
  useSetupProfilePanel.mockReturnValue({
    isLoading: false,
    userCardProps: { name: 'имя по умолчанию' },
    activityFeedProps: { profileId: 'default-profile' },
  });
};

describe('🐛 spec ProfilePanel: Shallowly', () => {
  it('🧪 собирает карточку и ленту с данными setup-хука', () => {
    expect.hasAssertions();

    //☣️ Arrange
    mockDefault();
    const userCardProps = { name: 'имя из хука' };
    const activityFeedProps = { profileId: 'profile-42' };
    useSetupProfilePanel.mockReturnValue({
      isLoading: false,
      userCardProps,
      activityFeedProps,
    });

    //🔥 Act
    const wrapper = shallow(<ProfilePanel />);

    //❓ Assert
    expect(wrapper.find(UserCard).props()).toEqual(userCardProps);
    expect(wrapper.find(ActivityFeed).props()).toEqual(activityFeedProps);
  });
});
```

Shallowly выполняет `ProfilePanel` и даёт посмотреть на возвращённое дерево React-элементов. Элемент `UserCard` в нём есть, его пропсы доступны. Но тело самой карточки не вызывается. До её чтения контекста дело не доходит. С `ActivityFeed` то же самое.

Поэтому оба ребёнка импортированы настоящими: по ним я нахожу нужные элементы. Для их рендера не нужны ни заглушки, ни провайдеры. Setup-хук панели при этом замокан явно — его ответ задаёт условия теста.

В обоих вариантах мы проверили одну и ту же связь: подготовленные данные попали в нужные дочерние элементы. В варианте с RTL для этого потребовались моки детей и их история вызовов. В Shallowly смотрим на сами элементы.

Если завтра внутри карточки появится ещё один хук, этот shallow-тест панели не потребует нового провайдера. Если вместо `UserCard` панель начнёт возвращать другой компонент, проверка упадёт: нужного элемента больше нет. Это изменение самой сборки панели, и его я как раз хочу заметить.

## Что всё-таки приходится мокать

Shallowly не избавляет от всех подмен. Зависимости, которые выполняет сам проверяемый компонент, остаются. В моём варианте это `useSetupProfilePanel`, поэтому его мок есть в обоих тестах.

Полного React-рендера у Shallowly нет. Если корневой компонент напрямую вызывает `useState`, `useContext` или другой React-хук, нельзя просто оставить этот вызов и ждать, что всё заработает как в RTL. Поэтому в этом тесте я подменяю setup-хук целиком. Его настоящую работу проверяю отдельно. React описывает, [почему вызов компонента и хуков связан с работой самого React](https://react.dev/reference/rules/react-calls-components-and-hooks).

И ещё одна граница: не выполнить тело ребёнка и не загрузить его модуль — разные вещи. Импорты никуда не исчезают. Если модуль при загрузке лезет в `window` или запускает побочный эффект, shallow сам по себе это не отменит. С такой зависимостью придётся разобраться отдельно.

Я не стал бы переписывать весь проект только ради тестового инструмента. Разделение на setup-хук и разметку мне удобно при работе с кодом; этот способ тестирования подходит к уже выбранному разделению.

## И да, скорость

Когда гоняешь тесты после правок, время ожидания имеет значение. Мне хочется быстро получить ответ на небольшой вопрос к компоненту.

В этом примере shallow-тест запускается в окружении Node. Ему не нужен jsdom, не нужно монтировать DOM-дерево и исполнять тела детей. Вариант с RTL использует jsdom и React-рендер. Подменённые дети возвращают `null`, поэтому их настоящая логика там тоже не выполняется — было бы нечестно приписывать её стоимость этому варианту.

Для такой узкой проверки у Shallowly меньше работы, связанной с рендером. Но это ещё не готовый результат бенчмарка. У полного запуска есть другие расходы: старт тестового раннера, преобразование файлов, импорты, подготовка окружения. На маленьком примере они могут занять больше времени, чем сами проверки.

Конкретные цифры сравню в [отдельном бенчмарке](https://github.com/bad4iz/shallowly/issues/24): одинаковые сценарии, повторные запуски и отдельно время самих тестов, старта и повторного прогона. Пока таких замеров нет, коэффициенты ускорения придумывать не буду.

Количество моков и время их поддержки секундомером раннера тоже не измеришь. Но для меня они входят в стоимость теста наравне со временем выполнения.

## А что будет видно только с настоящими детьми

Оба изолированных теста могут пройти, даже если настоящая карточка перестала показывать имя. Родитель передал правильное значение, а ребёнок им не воспользовался. Наши проверки панели этого не обещали замечать.

Через RTL можно отрисовать панель с настоящими детьми, подключить два провайдера и проверить, что имя и активность действительно появились на экране. Такой тест тоже есть в примере. Моков детей в нём нет, а провайдеры дают данные, которые им нужны.

Это полезная проверка взаимодействия. Она видит больше и при падении может потребовать поиска причины в нескольких компонентах. Для неё я готов собрать окружение, потому что хочу проверить именно совместную работу.

А в каждом изолированном тесте панели снова описывать, каких детей React не должен исполнять, мне не хочется. Для этой работы и выбираю Shallowly. Проверки пользовательских действий оставляю RTL или браузерным тестам: нажатие, фокус и изменение интерфейса нужно наблюдать там, где они действительно происходят.

## Код можно прогнать

В репозитории статьи лежит [полный пример](https://github.com/bad4iz/unit-test-article/tree/03499aa5425194bac5eb5a61b53f653abd05e6b7/examples/isolated-panel). В нём одинаковые сценарии для RTL и Shallowly: разметка панели, данные для детей и загрузка. Отдельно — DOM-тест с настоящими дочерними компонентами.

Чтобы получить именно эту версию примера:

```bash
git clone https://github.com/bad4iz/unit-test-article.git
cd unit-test-article
git checkout 03499aa5425194bac5eb5a61b53f653abd05e6b7
cd examples/isolated-panel
npm ci
npm test
```

Версии закреплены в `package-lock.json`: Shallowly 1.1.2, React 19.2.4, React Testing Library 16.3.0, Vitest 4.0.18 и jsdom 26.1.0. Команды и устройство примера описаны в его README. Сравнения производительности этот запуск не делает.
