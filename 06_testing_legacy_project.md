# И хочется, и колется: как начать писать тесты, когда в проекте много сложных букав

> Рабочий черновик. Полный текст ведётся в репозитории; [на Хабре](https://habr.com/ru/articles/1098488/) пока только заготовка. Редакторские вопросы и границы проверенного — в [заметках к статье](notes/06_testing_legacy_project.md).

Открываешь компонент на полторы тысячи строк. Хотел написать первый тест, но пока написал только `describe`.

Приложение работает, задачи приезжают, тестов почти нет. Хочется это исправить, но первая же попытка быстро превращается в отдельную работу: поднять окружение, замокать зависимости, понять, почему функция расчёта заодно что-то сохраняет и обновляет на странице.

А потом включаешь coverage. Написал несколько полезных тестов, прогнал — и получил крошечный процент по всему проекту. Если теперь поставить общий порог в 80%, первый MR с тестами никогда не станет зелёным.

Я предлагаю начать с участка, который уже приходится менять по задаче. Зафиксировать его поведение, сделать небольшие улучшения и договориться, что именно мы требуем от покрытия в этом MR. Старый код никуда не исчезнет, но перестанет быть условием «сначала покрой всё, потом начинай».

Сначала разберём первые проверки и небольшие изменения кода, затем — требования к coverage в MR. С покрытием у меня была отдельная история: обсуждения с командой Vitest и свой скрипт, который явно задаёт файлы для отчёта. С тех пор в Vitest появились новые возможности; до них тоже доберёмся.

## Начать с задачи, которая уже есть

Допустим, нужно поправить расчёт заказа. Здесь и начинаем: сумма товаров, скидка, доставка. Не надо заодно покрывать авторизацию и переносить все компоненты в новую структуру каталогов.

Перед изменением полезно ответить на три приземлённых вопроса:

- Какое поведение сейчас должно сохраниться?
- Какой сценарий меняет задача или исправляет баг?
- На каком уровне это поведение уже можно наблюдать?

Последний вопрос часто неприятный. Хочется маленький юнит-тест, а доступна только большая функция с хранилищем и DOM. Первый тест вполне может получиться шире, чем хотелось. Сначала он даст опору для изменений. Потом часть проверок получится перенести к выделенному расчёту.

Если задача исправляет баг, отдельно фиксируем воспроизведение с ожидаемым правильным результатом. Этот тест до исправления будет красным. Остальные проверки сохраняют уже нужное поведение: рефакторинг не должен попутно поменять правила соседних сценариев.

## А если к функции вообще не подступиться

Возьмём учебную функцию расчёта заказа. Цены храним в копейках. Функция читает корзину, считает сумму, показывает её на странице и сохраняет итог.

```javascript
import { cartStorage } from './cartStorage.js';
import { orderView } from './orderView.js';

export function updateOrderSummary(coupon = '') {
  const items = cartStorage.readItems();
  let subtotal = 0;

  for (const item of items) {
    subtotal += item.price * item.quantity;
  }

  const discount = coupon === 'SAVE10' ? Math.round(subtotal * 0.1) : 0;
  const delivery = subtotal === 0 || subtotal >= 500_000 ? 0 : 30_000;
  const total = subtotal - discount + delivery;

  orderView.showTotal(total);
  cartStorage.saveTotal(total);

  return total;
}
```

Здесь уже существуют два адаптера: `cartStorage` и `orderView`. За них можно зацепиться и подменить внешние эффекты. Это упрощает получение первого теста.

Если исходная функция напрямую ходит в сеть, читает глобальное состояние и трогает DOM, сначала ищем доступную проверку снаружи. Иногда проще добавить один интеграционный тест с подготовленным окружением. Иногда нужно первым небольшим изменением выделить чтение или запись в адаптер, сохранив порядок вызовов и обработку ошибок.

Это самое скользкое место: тестов ещё мало, а код уже приходится менять. Я бы не совмещал здесь выделение зависимостей, замену алгоритма и новую бизнес-логику. Сделал минимальный перенос, проверил известный сценарий, просмотрел diff. Потом добавил автоматическую проверку доступной границы. Ручная проверка на первом шаге бывает необходима, но считать её равноценной защите тестами не стоит.

## Сначала зафиксировать то, что уже работает

В нашем примере есть поведение, которое легко незаметно поменять: бесплатная доставка определяется по стоимости товаров **до скидки**. Корзина на 5000 рублей с промокодом `SAVE10` даёт итог 4500 рублей. Если при рефакторинге переставить условие и смотреть на сумму после скидки, доставка снова станет платной и получится 4800.

Это и стоит проверить до переноса кода. В статье использую встроенный `node:test`, чтобы учебный пример запускался без установки зависимостей. Те же сценарии можно перенести в существующий Vitest или Jest проекта.

```javascript
import assert from 'node:assert/strict';
import { test } from 'node:test';

import { updateOrderSummary } from './src/01-before.js';
import { mockDefault } from './support/mockDefault.js';

test('сохраняет бесплатную доставку и применяет итог со скидкой', (context) => {
  //☣️ Arrange
  const { items, effects } = mockDefault(context);
  items[0].price = 500_000;
  items[0].quantity = 1;

  //🔥 Act
  const total = updateOrderSummary('SAVE10');

  //❓ Assert
  assert.equal(total, 450_000);
  assert.deepEqual(effects, [
    ['showTotal', 450_000],
    ['saveTotal', 450_000],
  ]);
});
```

[`mockDefault(context)`](examples/legacy-order/support/mockDefault.js) создаёт свежую корзину и подменяет чтение, вывод и запись через `context.mock.method`. Вместо настоящих DOM и хранилища собирается список `effects`. Моки принадлежат контексту текущего теста и восстанавливаются автоматически; `beforeEach` и ручная очистка здесь не нужны. Проверяем и возвращённое число, и то, что эта же сумма ушла в оба адаптера.

Заодно нужны пустая корзина, сумма ниже порога, несколько товаров с количеством, неизвестный промокод и округление скидки. Ожидаемые результаты записываем явно; вычислять их той же функцией, которую проверяем, бессмысленно.

Такие проверки фиксируют наблюдаемое поведение исходного кода. Если обнаружили странность, не надо молча закреплять её как вечное требование. Разбираемся, нужна ли она пользователям, и отдельно оформляем изменение. Но менять правило доставки «заодно с наведением порядка» — плохой сюрприз для ревьюера.

В [запускаемом примере](examples/legacy-order) один набор сценариев проверяет все три состояния функции: до изменений, после выделения расчёта и после разделения чтения с записью. Проверяются сумма и внешние эффекты. Так видно, что мы сохранили старый вызов, а не просто написали тест под новую реализацию.

## Выделяем расчёт небольшим шагом

Здесь мне нравится подход Фаулера из «Рефакторинга кода на JavaScript»: небольшие преобразования с сохранением наблюдаемого поведения. В [описании книги](https://martinfowler.com/books/refactoring.html) это сформулировано как основа процесса. Для нашего первого шага подходит [Extract Function](https://refactoring.com/catalog/extractFunction.html).

Переносим расчёт как есть. Не заменяем цикл на `reduce`, не меняем округление и не придумываем новый порядок скидок.

```javascript
export function calculateOrderTotal(items, coupon = '') {
  let subtotal = 0;

  for (const item of items) {
    subtotal += item.price * item.quantity;
  }

  const discount = coupon === 'SAVE10' ? Math.round(subtotal * 0.1) : 0;
  const delivery = subtotal === 0 || subtotal >= 500_000 ? 0 : 30_000;
  const total = subtotal - discount + delivery;

  return total;
}
```

Старый вызов остаётся на месте:

```javascript
export function updateOrderSummary(coupon = '') {
  const items = cartStorage.readItems();
  const total = calculateOrderTotal(items, coupon);

  orderView.showTotal(total);
  cartStorage.saveTotal(total);

  return total;
}
```

Теперь расчёту нужны только входные данные. Его можно проверить без DOM, хранилища и моков:

```javascript
import assert from 'node:assert/strict';
import { test } from 'node:test';

import { calculateOrderTotal } from './src/calculateOrderTotal.js';

test('сохраняет бесплатную доставку при скидке на корзину от 5000 рублей', () => {
  //☣️ Arrange
  const items = [{ price: 500_000, quantity: 1 }];

  //🔥 Act
  const total = calculateOrderTotal(items, 'SAVE10');

  //❓ Assert
  assert.equal(total, 450_000);
});
```

Проверка старого `updateOrderSummary()` при этом остаётся: нужно убедиться, что он использует расчёт, показывает сумму и сохраняет её. Чистые тесты формулы эту связь не проверяют.

## Отдельно получить результат, отдельно применить

На предыдущем шаге уже можно остановиться, если этого достаточно для текущей задачи. Допустим, позже понадобилось показывать предварительный расчёт, не записывая итог. Тогда появляется конкретная причина разделить ещё две обязанности.

Для этого подходит [Separate Query from Modifier](https://refactoring.com/catalog/separateQueryFromModifier.html): отдельно получить значение, отдельно выполнить изменение.

```javascript
export function getOrderTotal(coupon = '') {
  const items = cartStorage.readItems();
  return calculateOrderTotal(items, coupon);
}

export function applyOrderTotal(total) {
  orderView.showTotal(total);
  cartStorage.saveTotal(total);
}

export function updateOrderSummary(coupon = '') {
  const total = getOrderTotal(coupon);
  applyOrderTotal(total);
  return total;
}
```

`getOrderTotal()` читает хранилище, поэтому чистой функцией не стал. Зато он не записывает результат и не обновляет страницу. `applyOrderTotal()` применяет готовую сумму. Старый `updateOrderSummary()` сохраняет прежнее поведение для существующих вызывающих мест.

Это небольшой промежуточный шаг. Не обязательно сразу менять все вызовы в проекте и собирать из них огромный MR. Новому месту можно дать отдельный запрос суммы, а старые постепенно переводить тогда, когда до них дойдёт задача.

И это не пересказ универсального рецепта из книги. Приёмы взяты у Фаулера; последовательность получения первых тестов здесь выбрана под наш пример.

## Что будет с React-компонентом

С компонентом мысль похожая: подготовку данных и разметку иногда удобнее разделить. В предыдущей статье я использовал соглашение `useSetup[Component]`: setup-хук собирает данные и логику, компонент выбирает элементы для отображения.

Но разнести код по двум файлам само по себе недостаточно. Если хук по-прежнему тянет половину приложения, сложность просто переехала. Иногда первым разумным шагом будет вынести из него чистое вычисление, иногда — выделить обращение к сервису, иногда — оставить более широкий тест и пока ничего не делить.

Тесты помогают заметить неудобные зависимости. Решение о рефакторинге всё равно должно объясняться устройством самого кода: смешанными обязанностями, неявными входными данными или побочными эффектами, которые мешают использовать результат отдельно.

## Какой именно coverage мы хотим увидеть

Фраза «проверяем только то, что тронули в MR» звучит понятно, пока не начинаешь настраивать инструменты. Под ней скрываются разные вещи.

| Вопрос | Что выбираем |
| --- | --- |
| Какие тесты запускать? | Все тесты или тесты, связанные с изменёнными исходниками |
| По каким файлам строить отчёт? | Весь проект или выбранные исходные файлы целиком |
| Какие строки учитывать в проценте? | Все исполняемые строки выбранных файлов или только строки из diff |

Выбор связанных тестов сам по себе не решает два остальных вопроса. Тест изменённого модуля может выполнять общую утилиту. Часть её сценариев останется в других тестовых файлах, которые в сокращённый прогон не попали. Полученный процент будет описывать этот прогон, а не всё, что существующие тесты знают об утилите.

Мой скрипт решает задачу на уровне **целых изменённых файлов**. Это существенно: поменял пять строк в файле на тысячу строк — в отчёте окажется весь файл. Назвать такой отчёт покрытием только нового кода было бы неправильно.

Если команда хочет порог именно по добавленным и изменённым строкам, понадобится сопоставить отчёт покрытия с Git diff. Там отдельно придётся решить, что делать с переносами кода, переименованиями и строками, которые инструмент вообще не считает исполняемыми. Один флаг выбора тестов за нас эту политику не определит.

Сам coverage тоже не знает, хорошая ли проверка. Можно выполнить расчёт и не проверить сумму. Зелёные строки получатся, а ошибку в результате такой тест пропустит. Поэтому сначала смотрю на сценарии и ожидания, потом на непокрытые ветки.

## Как я обсуждал это с Vitest

19 февраля 2024 года я открыл [issue #5237](https://github.com/vitest-dev/vitest/issues/5237). В воспроизведении был Vitest 1.2.2. Новый исходник без тестов не попадал в нужный отчёт, а сочетание тогдашнего `coverage.all` с `--changed` захватывало лишние файлы. Мне требовалось видеть непокрытый новый код, не получая заодно весь старый проект в знаменателе.

По моей issue 14 марта приняли [доработку #5314](https://github.com/vitest-dev/vitest/pull/5314): в PR прямо указано, что он закрывает #5237. Так что эту доработку покрытия при запуске с `--changed` я действительно помог инициировать. Отдельный вопрос — сколько тестов запускать, чтобы учесть все обращения к общим зависимостям, — этим изменением не закрыли.

2 июля я вернулся с [issue #6020](https://github.com/vitest-dev/vitest/issues/6020). При сокращённом прогоне покрытие зависимостей отличалось от полного. В обсуждении команда объяснила, почему не хочет автоматически расширять `--changed` до всех тестов общих модулей: через популярную утилиту такой запуск легко разрастается почти до полного.

Дальше разговор пришёл к явному ограничению отчёта через `coverage.include` и `exclude`. Я спросил, как получать нужный список автоматически для CI; в [обсуждении предложили использовать Git](https://github.com/vitest-dev/vitest/issues/6020#issuecomment-2235822057). В своём проекте я пошёл этим путём.

Jest в той переписке тоже всплывал: [сравнение привёл участник команды Vitest](https://github.com/vitest-dev/vitest/issues/5237#issuecomment-1962295793). С командой Jest я отдельно это не обсуждал. И поведение из воспроизведения 2024 года не стоит автоматически переносить на сегодняшние версии обоих инструментов.

## Явно перечислить файлы оказалось удобнее

В рабочем проекте у меня есть скрипт, который собирает список изменений и передаёт каждый выбранный исходник в `coverage.include`. Почти ручное управление, только сам список составляет Git.

Покажу алгоритм с обезличенными названиями:

```text
Определить целевую ветку MR.

Собрать пути:
  изменения ветки от общего предка с целевой веткой;
  staged-изменения;
  unstaged-изменения отслеживаемых файлов.

Если изменились зависимости или конфигурация тестирования:
  выполнить полный прогон и общий отчёт покрытия.

Иначе:
  выбрать существующие исходники из собранного списка;
  исключить тестовые и технические файлы;
  передать пути в coverage.include;
  запустить тесты, связанные с изменениями.

Если менялись только тесты:
  выполнить связанный прогон без расчёта покрытия.
```

Важная деталь — общая точка ветвления. Для ветки MR нужна разница от её общего предка с целевой веткой. Например, `git diff origin/main...HEAD` и `git diff origin/main HEAD` могут дать разные списки. Во втором случае на результат влияют и изменения, которые успели попасть в `main` после ответвления нашей ветки.

Набор запускаемых тестов и область отчёта здесь выбираются отдельно. Это позволяет явно увидеть: вот эти файлы я включил в coverage. Если исходник выбран, но его ни один тест не исполнил, он должен оставаться в отчёте с нулём, а не исчезать из проверки.

У моего варианта есть шероховатости. Внешний список из `git diff` не подхватывает новые untracked-файлы. Фильтр существующих исходников убирает удалённые файлы, поэтому изменение, состоящее только из удаления, может вообще не запустить проверку. Перед тем как переносить такую схему к себе, эти случаи стоит обработать явно.

Есть и ограничение самого сокращённого прогона: он опирается на известные инструменту связи между файлами. Динамически составленные пути, внешние ресурсы и изменения окружения могут потребовать полного запуска. Общий контроль в CI поэтому остаётся.

Порог тоже надо читать внимательно. Общие 10% по выбранным файлам не означают, что каждый из них покрыт хотя бы на 10%: один хорошо покрытый модуль может вытянуть среднее. Для требования к каждому файлу нужна отдельная настройка или проверка. Маленький стартовый порог помогает внедрить процесс, но сам по себе качество тестов не обеспечивает.

## Что появилось в новых версиях

В [Vitest 4.1, вышедшем 12 марта 2026 года](https://v4.vitest.dev/blog/vitest-4-1#coverage-for-changed-files-only), появилась отдельная настройка `coverage.changed`. Её добавили позже в [PR #9521](https://github.com/vitest-dev/vitest/pull/9521), который закрывает другое обращение — [#8747](https://github.com/vitest-dev/vitest/issues/8747). Теперь можно выполнить весь обычный набор тестов и ограничить отчёт изменёнными исходниками. Для этой задачи стоит сначала посмотреть на штатный режим, а уже потом тащить к себе мой скрипт.

Фрагмент **существующей** конфигурации Vitest 4.1+:

```javascript
test: {
  coverage: {
    enabled: true,
    changed: 'origin/main',
    include: ['src/**/*.{js,jsx,ts,tsx}'],
  },
}
```

Здесь `origin/main` — пример целевой ветки. Передаётся один ref: добавлять к нему `...HEAD` не нужно. Ветка и история для поиска общего предка должны быть доступны локально. Параметр ограничивает файлы покрытия; набор тестов отдельно могут ограничивать `test.changed` и другие фильтры проекта. [Документация `coverage.changed`](https://v4.vitest.dev/config/coverage#coverage-changed).

`include` задаёт кандидатов для отчёта, а `changed` оставляет среди них изменённые. Это по-прежнему покрытие файлов целиком. Настройка не превращает результат в процент по добавленным строкам MR. В опубликованных ранее примерах серии закреплён Vitest 4.0.18; в нём этой опции ещё нет.

У Jest также нужно разделять выбор тестов и область покрытия. [`--changedSince`, `--onlyChanged` и `--findRelatedTests`](https://jestjs.io/docs/cli) относятся к выбору тестов. [`collectCoverageFrom`](https://jestjs.io/docs/configuration#collectcoveragefrom-array) позволяет явно задать исходники для отчёта, в том числе не импортированные тестами. Например, сгенерированный из Git список можно положить в существующий конфиг:

```javascript
collectCoverageFrom: [
  'src/order/calculateOrderTotal.js',
  'src/order/updateOrderSummary.js',
],
```

После этого обычный `jest --coverage` без changed-фильтров запускает обычный полный набор тестов, а отчёт строится по выбранным исходникам. Конкретные пути здесь учебные. В своём проекте надо сохранить остальные настройки, исключения и согласованные пороги.

История со скриптом остаётся полезной даже при наличии готового флага: она заставляет сначала решить, какой отчёт мы хотим получить. Полный набор тестов с узким отчётом и быстрый сокращённый прогон — разные режимы работы.

## Что я хочу видеть в первом MR

У первого MR с тестами может быть вполне скромный результат: несколько зафиксированных сценариев, один выделенный расчёт и понятный отчёт по выбранному участку. Это уже можно проверить и принять.

В описании полезно назвать сохранённые правила, отдельно указать намеренное изменение поведения и объяснить область покрытия. Например: «Проверяем целиком два изменённых исходника; запускаем весь набор тестов. Общий процент проекта этой проверкой не ограничен». Ревьюеру не придётся угадывать, почему зелёная цифра вдруг выросла.

Для старых больших файлов не стал бы требовать произвольные 80% с первой правки. Можно договориться о проверке меняемой логики и понятном следующем шаге, а для новых небольших модулей сразу задать более строгие требования. Если старый долг временно исключён из обязательного порога, сам общий отчёт лучше сохранить: он показывает, сколько работы ещё осталось.

Следующая задача добавит ещё несколько сценариев. Исправленный баг — ещё один тест на воспроизведение. Постепенно станет меньше мест, которые приходится ковырять вслепую. Главное, чтобы тесты продолжали ловить ошибки, а поддержка отчёта не превратилась в отдельный способ обходить красный CI.

## Запустить пример

В [examples/legacy-order](examples/legacy-order) лежат три состояния реализации и тесты. Нужен Node.js 22 или новее, внешних зависимостей нет:

```bash
git clone --branch docs/testing-legacy-project https://github.com/bad4iz/unit-test-article.git
cd unit-test-article/examples/legacy-order
node --test
```

Пример проверяет расчёт и его взаимодействие с подменёнными адаптерами. Реальные DOM и `localStorage` в этих тестах не исполняются. Команды coverage из раздела про инструменты относятся к настройке вашего проекта; этот маленький пример на Node не воспроизводит историю Git, Vitest и Jest.
