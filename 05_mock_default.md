# beforeEach и afterEach — антипаттерн. Пора выкинуть их из ваших тестов

![Откуда в тесте эти данные? Подготовка сценария через mockDefault](assets/mock-default/cover-body.jpg)

Открываешь упавший тест. Действие есть, проверка есть, а откуда взялись данные — сходу не видно. Надо подняться к `beforeEach`, потом ещё выше: вдруг там внешний `describe` со своей подготовкой. Теперь можно вернуться к тесту и попробовать собрать всё в голове.

С парой коротких тестов это ещё терпимо. Когда появляются вложенные группы и переопределения моков, читать такой файл уже неприятно. Вроде пришёл разобраться с одним сценарием, а заодно изучаешь расписание его подготовки.

Поэтому у меня простое правило: в файлах юнит-тестов не использую `beforeEach`, `beforeAll`, `afterEach` и `afterAll` для подготовки сценариев и проверок. В начале каждого теста вызываю `mockDefault()`, а нужные отличия задаю следом. Служебную очистку моков оставляю настройкам тестового окружения.

Покажу, что делает эта функция, чего она не делает и как не превратить её в очередную проблему.

## Что не так с beforeEach

Возьмём функцию, которая получает профиль и собирает заголовок:

```javascript
import { fetchProfile } from './profileApi';

export async function getProfileHeading() {
  const profile = await fetchProfile();

  if (profile === null) {
    return 'Профиль не найден';
  }

  return `Профиль: ${profile.name}`;
}
```

Если источник вернул ошибку, функция передаёт её вызывающему коду. Никаких компонентов и DOM здесь нет: разговор именно о подготовке тестов. В запускаемом примере `fetchProfile` — локальная учебная функция, сеть не используется.

Замокаем модуль и вынесем обычный ответ в `beforeEach`. Для отсутствующего профиля добавим вложенную группу. Ниже фрагмент тестового файла:

```javascript
vi.mock('./profileApi');

describe('getProfileHeading', () => {
  beforeEach(() => {
    fetchProfile.mockResolvedValue({
      id: 'profile-1',
      name: 'имя по умолчанию',
      preferences: { locale: 'ru' },
    });
  });

  describe('если профиль не найден', () => {
    beforeEach(() => {
      fetchProfile.mockResolvedValue(null);
    });

    it('сообщает, что профиль не найден', async () => {
      const heading = await getProfileHeading();

      expect(heading).toBe('Профиль не найден');
    });
  });
});
```

Этот код работает. Порядок хуков определён, никакой случайности Vitest сюда не подмешивает. Но условия конкретного теста разбросаны по файлу. Внешний хук задаёт один ответ, внутренний его меняет, а внутри `it` про это ничего не сказано.

Чтобы добавить соседний сценарий, надо учитывать эту подготовку. Чтобы перенести тест в другую группу — тоже. Именно эта неявная зависимость мне и не нравится. Поэтому «нельзя» здесь — моё соглашение для тестовых файлов, а не запрет со стороны Vitest. Сами [хуки жизненного цикла](https://v4.vitest.dev/api/hooks) никуда не делись и работают как описано в документации.

## mockDefault — обычная функция

Это не API библиотеки. Имя `mockDefault` я использую для функции, которая задаёт обычные условия текущего теста. В нашем примере — создаёт профиль и настраивает ответ API.

```javascript
import { fetchProfile } from './profileApi';

/**
 * Создаёт свежий профиль и задаёт обычный ответ API для текущего теста.
 * Очередь разовых ответов и историю вызовов сбрасывает mockReset в конфигурации.
 *
 * @returns {{ profile: { id: string, name: string, preferences: { locale: string } } }}
 */
export const mockDefault = () => {
  const profile = {
    id: 'profile-1',
    name: 'имя по умолчанию',
    preferences: { locale: 'ru' },
  };

  fetchProfile.mockResolvedValue(profile);

  return { profile };
};
```

Здесь намеренно простые данные. По строке «имя по умолчанию» сразу видно, что это базовый ответ, а не какое-то особенное значение для одного сценария. Объект возвращаю из функции, чтобы тест мог взять его и поменять только нужное поле.

В репозитории helper лежит в `mockDefault.js`: его используют основной файл и отдельная демонстрация сброса моков. Если функция нужна одному тестовому файлу, спокойно оставляю её рядом с тестами. Выносить в общий каталог только ради самого выноса незачем.

## Как теперь выглядит тест

Модуль мокается через `vi.mock('./profileApi')`, ответы задаются прямо на импортированной функции. Примеры написаны на JavaScript.

```javascript
import { describe, expect, it, vi } from 'vitest';

import { getProfileHeading } from './getProfileHeading';
import { mockDefault } from './mockDefault';
import { fetchProfile } from './profileApi';

vi.mock('./profileApi');

describe('🐛 spec getProfileHeading: явная подготовка', () => {
  it('🧪 подставляет имя из профиля в заголовок', async () => {
    expect.hasAssertions();

    //☣️ Arrange
    mockDefault();

    //🔥 Act
    const heading = await getProfileHeading();

    //❓ Assert
    expect(heading).toBe('Профиль: имя по умолчанию');
  });

  it('🧪 использует другое имя из ответа API', async () => {
    expect.hasAssertions();

    //☣️ Arrange
    const { profile } = mockDefault();
    fetchProfile.mockResolvedValueOnce({ ...profile, name: 'другое имя' });

    //🔥 Act
    const heading = await getProfileHeading();

    //❓ Assert
    expect(heading).toBe('Профиль: другое имя');
  });

  it('🧪 сообщает, что профиль не найден', async () => {
    expect.hasAssertions();

    //☣️ Arrange
    mockDefault();
    fetchProfile.mockResolvedValueOnce(null);

    //🔥 Act
    const heading = await getProfileHeading();

    //❓ Assert
    expect(heading).toBe('Профиль не найден');
  });

  it('🧪 передаёт ошибку API вызывающему коду', async () => {
    expect.hasAssertions();

    //☣️ Arrange
    mockDefault();
    const error = new Error('Профиль временно недоступен');
    fetchProfile.mockRejectedValueOnce(error);

    //🔥 Act
    const result = getProfileHeading();

    //❓ Assert
    await expect(result).rejects.toBe(error);
  });
});
```

Повторяется одна строка `mockDefault()`. Меня это устраивает: она явно обозначает начало подготовки. После неё видно всё, чем текущий сценарий отличается от обычного. Нет необходимости раскручивать вложенные `describe` в поисках последнего переопределения.

В тесте ошибки `getProfileHeading()` вызывается в Act, а отклонение промиса проверяется в Assert. Проверку обязательно ждём через `await`, иначе тест может закончиться раньше неё.

`mockResolvedValueOnce` здесь подходит, потому что функция делает один запрос. Если в другом сценарии все обращения должны получать одинаковый ответ, использую `mockResolvedValue`. Суффикс `Once` не нужно лепить везде по привычке: после разового ответа мок вернётся к обычной реализации.

## А кто сбрасывает моки

Само название `mockDefault` ничего не очищает. Без настройки окружения предыдущий тест вполне может оставить нам сюрприз.

Для примера использую Vitest **4.0.18** с такой конфигурацией:

```javascript
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    environment: 'node',
    include: ['src/**/*.test.js'],
    mockReset: true,
    restoreMocks: true,
  },
});
```

[`mockReset: true`](https://v4.vitest.dev/config/mockreset) перед каждым тестом сбрасывает историю вызовов, поведение мок-функций и очереди разовых ответов. Затем тест вызывает `mockDefault()` и получает нужные исходные условия. Поэтому вручную вызывать `vi.resetAllMocks()` внутри helper не требуется.

[`restoreMocks: true`](https://v4.vitest.dev/config/restoremocks) нужен для восстановления методов, подменённых через `vi.spyOn`. В этом примере таких методов нет; настройку оставляю для тестов, в которых они появятся. В Vitest 4 она не отменяет модульный `vi.mock` и не заменяет `mockReset`.

А вот `clearMocks` только очищает историю вызовов. Реализация и неиспользованные разовые ответы остаются. Можно вызвать `mockDefault()`, заново назначить обычный ответ и всё равно получить старый `mockResolvedValueOnce`, который предыдущий тест не успел использовать. Новый обычный ответ не вычищает очередь разовых. [Разница между очисткой и сбросом](https://v4.vitest.dev/api/mock#mockreset) здесь вполне практическая.

В репозитории есть отдельная демонстрация: один тест меняет вложенные данные и оставляет лишний разовый ответ, следующий проверяет свежий профиль и чистое состояние мока. С `mockReset: true` она проходит. Если отключить сброс, следующий тест получает оставшийся ответ и падает.

Два теста в этой демонстрации намеренно запускаются последовательно, чтобы проверить именно переход между ними. Обычные сценарии `getProfileHeading` такой связи не имеют.

## Почему не beforeAll и что делать с after

`beforeAll` выполняется один раз на группу. Если в нём создать изменяемый объект, а потом раздать тестам одну ссылку, мутации никуда сами не исчезнут. Один тест поменял вложенный `preferences`, соседний получил уже изменённые данные. Сброс mock-функций этот объект не восстановит.

Есть и менее очевидный момент: с `mockReset: true` ответ, настроенный в `beforeAll`, сбрасывается ещё до первого теста. В Vitest 4.0.18 автоматический сброс происходит после `beforeAll`, но перед `beforeEach` и телом теста. Это видно в [порядке подготовки теста](https://github.com/vitest-dev/vitest/blob/v4.0.18/packages/vitest/src/runtime/runners/test.ts). Поэтому перенести настройку моков в `beforeAll` ради «сделаем один раз» здесь не получится.

У `afterEach` другая задача, но в нём тоже легко спрятать часть сценария. Например, проверку «запрос обязательно был отправлен» или ручное возвращение бизнес-данных в обычное состояние. Тогда конец теста находится где-то отдельно от самого теста. Проверки я держу в Assert, а данные создаю заново в следующем Arrange. `afterAll` для изоляции соседних тестов вообще слишком поздний: он выполнится, когда вся группа уже закончилась.

При этом служебную очистку убирать не предлагаю. Размонтирование React-дерева, возврат настоящих таймеров, закрытие временного ресурса — работа тестового окружения. Например, `afterEach(cleanup)` можно зарегистрировать в общем `setupFiles`, если выбранная конфигурация сама не подключает очистку. Это не скрытые условия конкретного сценария.

Для интеграционных тестов запуск дорогого ресурса на группу через `beforeAll`/`afterAll` тоже может быть разумным. Но данные каждого сценария всё равно должны быть изолированы. Моё правило про явный Arrange не делает lifecycle-хуки запрещённой технологией во всём проекте.

## Запретить хуки можно прямо в ESLint

Чтобы не ловить очередной `beforeEach` руками на ревью, это соглашение можно закрепить линтером. Причём писать своё правило не придётся:

- В [`eslint-plugin-jest` есть `jest/no-hooks`](https://github.com/jest-community/eslint-plugin-jest/blob/main/docs/rules/no-hooks.md).
- В [`@vitest/eslint-plugin` есть `vitest/no-hooks`](https://github.com/vitest-dev/eslint-plugin-vitest/blob/main/docs/rules/no-hooks.md).

Оба правила запрещают вызовы `beforeEach`, `beforeAll`, `afterEach` и `afterAll`. В документации Jest среди причин прямо указано общее состояние между тестами, а вместо хуков показаны обычные функции подготовки, которые вызываются внутри `it`. То есть сам подход давно существует; `mockDefault` — моё название для такой функции.

В `recommended` обоих плагинов `no-hooks` не включён. Запрет надо выбрать явно. Для Vitest минимальная настройка выглядит так:

```bash
npm install --save-dev eslint @vitest/eslint-plugin
```

```javascript
// eslint.config.mjs
import vitest from '@vitest/eslint-plugin';

export default [
  {
    files: ['src/**/*.test.js'],
    plugins: { vitest },
    rules: {
      'vitest/no-hooks': 'error',
    },
  },
];
```

Это [flat config для ESLint 9+](https://github.com/vitest-dev/eslint-plugin-vitest#usage). В существующем проекте такой блок добавляется к остальной конфигурации. Шаблон `files` нужно подогнать под свои **юнит-тесты**: общий `setupFiles` со служебной очисткой и интеграционные тесты с отдельными ресурсами под этот запрет не подводим. Конфигурация выше рассчитана на JavaScript, как и примеры статьи; для TypeScript нужен ещё настроенный парсер.

Для Jest устанавливаем `eslint-plugin-jest`, импортируем `jest` из него, регистрируем `plugins: { jest }` и включаем `'jest/no-hooks': 'error'`.

У обоих правил есть опция `allow`. Например, `['error', { allow: ['afterEach', 'afterAll'] }]` оставит разрешёнными хуки очистки, а `beforeEach` и `beforeAll` запретит. Линтер при этом не разбирается, что именно спрятано в разрешённом хуке: служебная очистка или проверка бизнес-сценария. Поэтому область действия правила всё равно надо выбрать осознанно.

У Testing Library есть более точечное правило — [`testing-library/no-render-in-lifecycle`](https://github.com/testing-library/eslint-plugin-testing-library/blob/main/docs/rules/no-render-in-lifecycle.md) из `eslint-plugin-testing-library`. Оно запрещает `render` и пользовательские обёртки над ним в `beforeEach` и `beforeAll`: рендер должен быть ближе к проверкам. Причём это правило уже включено в пресет `react`. Полного запрета хуков оно не вводит.

Рядом есть ещё несколько правил, которые помогают не превращать тест в квест:

- [`vitest/no-conditional-expect`](https://github.com/vitest-dev/eslint-plugin-vitest/blob/main/docs/rules/no-conditional-expect.md) запрещает условные проверки. Если `expect` спрятан под `if`, тест может стать зелёным, так до него и не добравшись.
- [`vitest/no-conditional-in-test`](https://github.com/vitest-dev/eslint-plugin-vitest/blob/main/docs/rules/no-conditional-in-test.md) запрещает условную логику внутри теста. Разные сценарии проще разобрать, когда у каждого свой `it` или строка в `it.each`.
- [`vitest/max-nested-describe`](https://github.com/vitest-dev/eslint-plugin-vitest/blob/main/docs/rules/max-nested-describe.md) ограничивает глубину вложенных групп. Например, `['error', { max: 2 }]` не даст построить ещё пять этажей `describe`.

В `eslint-plugin-jest` есть [те же три правила с префиксом `jest/`](https://github.com/jest-community/eslint-plugin-jest#rules). Они не заставят написать хороший тест, но часть косяков поймают ещё до ревью. Сам `mockDefault()` линтер за нас не вызовет — явная подготовка остаётся соглашением команды.

## Как не испортить mockDefault

**Вызывать в начале Arrange.** Сначала базовые условия, затем отличия сценария, затем действие. Если настроить особый ответ до `mockDefault()`, helper может его перезаписать.

**Создавать свежие данные.** `profile` находится внутри функции вместе с вложенным `preferences`. Просто сделать `{ ...sharedProfile }` недостаточно: вложенные объекты останутся общими. И автоматический reset эту проблему не починит.

**Держать обычный сценарий маленьким.** В helper нужны зависимости тестируемого кода. Если туда постепенно съезжаются моки всех страниц приложения, пора разбирать эту кучу. Тест функции формирования заголовка не должен заодно готовить корзину и авторизацию.

**Показывать отличия в самом тесте.** Вызов `mockDefault(true, false, true)` требует расшифровки. Здесь достаточно обычного `mockDefault()` и строки `fetchProfile.mockResolvedValueOnce(null)`: сразу понятно, что именно изменилось. Именованные параметры можно добавить, когда они действительно сокращают повторяющуюся подготовку; предусматривать все будущие сценарии заранее не надо.

**Не прятать действие и проверки в helper.** `mockDefault()` готовит входные данные и ответы зависимостей. Он не вызывает `getProfileHeading()`, не проверяет результат и не запускает соседний сценарий. Иначе Act и Assert снова разъедутся по файлу, только теперь без `beforeEach`.

**Ждать реальную асинхронную подготовку.** Наш helper синхронный: `mockResolvedValue` только настраивает будущий ответ, поэтому `await mockDefault()` здесь лишний. Если подготовке действительно нужно дождаться асинхронной операции, делаем helper асинхронным и явно ждём его в Arrange:

```javascript
// Для helper, который действительно выполняет асинхронную подготовку.
//☣️ Arrange
const { profile } = await mockDefault();
```

**Не путать свежие моки со свежим окружением.** `mockDefault()` не сбрасывает модульные переменные, DOM, таймеры или данные в базе. Для них нужны свои механизмы очистки и изоляции.

**Не запускать сценарии с одним общим мок-модулем через `test.concurrent`.** Пока один тест ждёт промис, другой может поменять ответ той же функции. Явный вызов helper эту гонку не устранит. В примере тесты внутри файла последовательные; параллельный запуск независимых файлов отключать не требуется. [Vitest отдельно предупреждает об общих моках в конкурентных тестах.](https://v4.vitest.dev/config/mockreset)

[Полный пример с конфигурацией и lockfile](https://github.com/bad4iz/unit-test-article/tree/c1b2a43ca24cddd883a7816078b9995dc4f2e3ed/examples/mock-default). Нужен Node.js 22.12+ в ветке 22 либо Node.js 24.

```bash
git clone --branch docs/mock-default-test-setup https://github.com/bad4iz/unit-test-article.git
cd unit-test-article
git checkout c1b2a43ca24cddd883a7816078b9995dc4f2e3ed

npm ci
npm test
```

В примере восемь тестов: четыре основных сценария, два для сравнения с вариантом на `beforeEach` и два для демонстрации сброса моков и свежих данных. Все восемь проходят на указанной версии Vitest.

Мне достаточно открыть один `it` и увидеть: вот обычные условия, вот отличие этого сценария, вот действие и результат. За эту возможность я спокойно плачу одной повторяющейся строкой `mockDefault()`.
