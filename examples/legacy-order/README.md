# Первые тесты и небольшие изменения расчёта заказа

Учебный фрагмент: чтение корзины, расчёт, обновление страницы и запись итога собраны в одной функции. Здесь нет попытки воспроизвести огромный продовый модуль целиком. `cartStorage` и `orderView` — уже существующие границы зависимостей, за которые можно зацепиться в тесте. Если таких границ в приложении нет, их создание будет отдельным небольшим изменением, которое тоже нужно проверить.

Нужен Node.js 22 или новее. Зависимостей нет, установка пакетов не нужна:

```bash
npm test
```

Или напрямую:

```bash
node --test
```

Три версии одного публичного вызова:

1. `src/01-before.js` — исходный `updateOrderSummary(coupon)`, смешивающий расчёт и эффекты.
2. `src/02-extract-function.js` — тот же вызов после выделения `calculateOrderTotal(items, coupon)`. Алгоритм перенесён без изменения условий.
3. `src/03-separate-query.js` — `getOrderTotal()` получает сумму без записей, `applyOrderTotal(total)` обновляет страницу и хранилище. Старый `updateOrderSummary()` остаётся совместимым фасадом: по-прежнему выполняет эффекты и возвращает итог. Это разделение внутри реализации; старый публичный вызов всё ещё совмещает обе обязанности ради совместимости.

Суммы заданы в копейках. `SAVE10` уменьшает стоимость товаров на 10%, скидка округляется до копейки. Доставка стоит 300 рублей и бесплатна при стоимости товаров от 5000 рублей **до скидки**. Пустая корзина не требует доставки. Это зафиксированное поведение исходного примера, а не универсальные правила магазина.

Общий набор проверок запускается для всех трёх версий. Он проверяет сумму, порядок видимых эффектов и передачу ошибки чтения без новых записей. Отдельные тесты проверяют выделенный расчёт и возможность запросить сумму без обновления страницы. Ожидания записаны числами; они не вычисляются через новую реализацию.

`mockDefault(context)` в каждом тесте создаёт свежие данные и подменяет только две внешние границы. Моки принадлежат `TestContext` Node.js и автоматически восстанавливаются после теста. В чистом расчёте моки не нужны. `beforeEach`/`afterEach` не используются.

Это проверки бизнес-расчёта и его связи с адаптерами. Настоящие DOM и `localStorage` здесь не запускаются; для проверки браузерной интеграции нужен отдельный сценарий. Валидация входных данных и ошибки записи не входят в этот небольшой пример.

Названия приёмов и сохранение поведения опираются на [Extract Function](https://refactoring.com/catalog/extractFunction.html), [Separate Query from Modifier](https://refactoring.com/catalog/separateQueryFromModifier.html) и [описание рефакторинга Фаулером](https://martinfowler.com/books/refactoring.html). Последовательность получения первых тестов в статье — применение этих идей к нашему примеру, а не пересказ единого алгоритма из этой книги.
