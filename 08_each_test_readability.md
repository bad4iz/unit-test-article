# Хватит пихать всё в it.each. Это потом вам дебажить

> Рабочий черновик. Полный текст ведётся в репозитории; [на Хабре](https://habr.com/ru/articles/1098686/) только заготовка. Вопросы к доработке — в [редакторских заметках](notes/08_each_test_readability.md).

Упал тест. Открываешь файл, находишь нужное название — а рядом массив. Действие где-то ниже, моки там же, проверка общая на несколько случаев. Ещё надо разобраться, что означает очередной `null` и почему в одной строке ожидается результат, а в другой ошибка.

Зато одинаковые строки убрали. Красота.

Вот к такой экономии у меня вопросы. Я хочу открыть упавший тест и прочитать его целиком: что подготовили, что вызвали, чего ждали. Когда ради этого надо прыгать между таблицей и общим callback, тест уже требует расшифровки. А если callback оброс условиями, приходится отлаживать ещё и эту маленькую программу подготовки.

Речь про `it.each`, `test.each`, `describe.each` и ручную генерацию похожих тестов. Покажу, где конкретно начинает мешать таблица и почему несколько отдельных `it` могут оказаться проще, даже если файл стал длиннее.

## Сначала всё выглядит удобно

Возьмём знакомую функцию: получила профиль — собрала заголовок. Профиля нет — вернула сообщение. Ошибка источника уходит вызывающему коду.

```javascript
import { fetchProfile } from './profileApi.js';

export async function getProfileHeading() {
  const profile = await fetchProfile();

  if (profile === null) {
    return 'Профиль не найден';
  }

  return `Профиль: ${profile.name}`;
}
```

В учебном примере источник локальный, без сети. В тестах модуль подменяется через `vi.mock('./profileApi.js')`, а обычный ответ задаёт `mockDefault()`:

```javascript
/**
 * Создаёт свежий профиль и задаёт обычный ответ источника для текущего теста.
 *
 * @returns {{ profile: { name: string } }}
 */
const mockDefault = () => {
  const profile = { name: 'имя по умолчанию' };
  fetchProfile.mockResolvedValue(profile);
  return { profile };
};
```

Служебный сброс моков включён в конфигурации Vitest: `mockReset: true`, `restoreMocks: true`. Внутри сценариев нет `beforeEach` и ручных сбросов. Подробно этот подход разбирается в [черновике про mockDefault](https://github.com/bad4iz/unit-test-article/blob/docs/mock-default-test-setup/05_mock_default.md).

Теперь соберём три сценария в одну таблицу. Имя у каждой строки сразу сделаем нормальным — проблема не сводится к плохим названиям:

```javascript
it.each([
  ['готовит заголовок с именем из API', { name: 'имя из API' }, null, 'Профиль: имя из API'],
  ['сообщает об отсутствии профиля', null, null, 'Профиль не найден'],
  ['передаёт ошибку источника', undefined, new Error('Сервис недоступен'), 'Сервис недоступен'],
])('🧪 %s', async (_title, profile, error, expected) => {
  expect.hasAssertions();

  //☣️ Arrange
  mockDefault();
  if (error) {
    fetchProfile.mockRejectedValue(error);
  } else {
    fetchProfile.mockResolvedValue(profile);
  }

  //🔥 Act
  const result = getProfileHeading();

  //❓ Assert
  if (error) {
    await expect(result).rejects.toThrow(expected);
  } else {
    await expect(result).resolves.toBe(expected);
  }
});
```

Тесты работают. Но у таблицы уже появилось несколько обязанностей. Вторая колонка задаёт ответ, третья переключает способ подготовки и проверки, четвёртая означает то готовый заголовок, то сообщение ошибки. `undefined` в последней строке стоит потому, что место под профиль есть, а сам профиль этому сценарию не нужен.

Чтобы прочитать одну строку, надо помнить сигнатуру callback. Чтобы понять callback — держать перед глазами строку. Для трёх случаев ещё можно потерпеть. Но зачем закреплять форму, которая усложняется с каждым новым отличием?

## Объекты помогут прочитать данные. Условия останутся

Первое разумное возражение: записать случаи объектами с именованными полями. Вместо позиций будут `name`, `profile`, `error`, `expected`, а название можно взять через `$name`. [Vitest](https://github.com/vitest-dev/vitest/blob/v4.0.18/docs/api/index.md#testeach) и [Jest](https://jestjs.io/docs/api#testeachtablename-fn-timeout) это умеют.

Согласен, читать станет легче. Больше не надо считать колонки. Но `expected` всё ещё означает две разные вещи, а внутри общего теста остаётся выбор между успешным ответом и ошибкой.

Можно переименовать его в два поля. Добавить флаг `shouldReject`. Потом ещё один: надо ли ждать повторный запрос. Вынести настройку в функцию. Передавать в таблице собственные `arrange` и `assert` для каждой строки. В какой-то момент мы уже собрали свой формат объявления тестов поверх формата, который дал Vitest.

Мне в таком месте проще написать обычные `it`. Они уже умеют иметь имя, подготовку, действие и проверку. Дополнительную схему данных для этого придумывать не надо.

## Дебажить можно. Но сначала собери сценарий

У `.each` каждая строка регистрируется отдельным тестом. У неё свой результат, и обычное падение одной строки не превращает остальные в непроверенный хвост того же теста. Это видно в [реализации Vitest 4.0.18](https://github.com/vitest-dev/vitest/blob/v4.0.18/packages/runner/src/suite.ts#L651).

Уникальное имя позволяет выбрать один случай. Например, для таблицы из нашего примера:

```bash
npx vitest run src/getProfileHeading.each.test.js -t "передаёт ошибку источника"
```

[`-t` фильтрует по полному имени теста](https://v4.vitest.dev/guide/filtering#filtering-by-test-name), включая окружающие `describe`. Отладчик тоже подключается: у Vitest есть [инструкции для IDE и Node Inspector](https://v4.vitest.dev/guide/debugging). Тут нет технического запрета на дебаг.

Неудобство начинается после того, как открыл код. В общем callback надо выяснить, с какими параметрами мы сюда пришли, какой мок выбрала подготовка и какая ветка проверки должна выполниться. Если запускать всю таблицу, точка останова в этом callback будет встречаться у разных случаев. Можно сузить запуск, поставить условную точку останова, посмотреть аргументы. Всё решаемо. Только хотелось разбираться с падением приложения, а не распаковывать устройство теста.

Отдельный `it` не починит плохой мок и не избавит от отладчика. Зато его условия лежат прямо перед глазами. Даже без запуска видно, что именно подменили и какой результат собирались получить.

## Теперь те же проверки без таблицы

Оставим ту же функцию, тот же модульный мок и тот же `mockDefault`. Меняем только форму тестов:

```javascript
it('🧪 готовит заголовок с именем из API', async () => {
  expect.hasAssertions();

  //☣️ Arrange
  const { profile } = mockDefault();
  fetchProfile.mockResolvedValue({ ...profile, name: 'имя из API' });

  //🔥 Act
  const result = await getProfileHeading();

  //❓ Assert
  expect(result).toBe('Профиль: имя из API');
});

it('🧪 сообщает об отсутствии профиля', async () => {
  expect.hasAssertions();

  //☣️ Arrange
  mockDefault();
  fetchProfile.mockResolvedValue(null);

  //🔥 Act
  const result = await getProfileHeading();

  //❓ Assert
  expect(result).toBe('Профиль не найден');
});

it('🧪 передаёт ошибку источника', async () => {
  expect.hasAssertions();

  //☣️ Arrange
  mockDefault();
  fetchProfile.mockRejectedValue(new Error('Сервис недоступен'));

  //🔥 Act
  const result = getProfileHeading();

  //❓ Assert
  await expect(result).rejects.toThrow('Сервис недоступен');
});
```

Да, `mockDefault()` и вызов функции повторяются. Зато сценарий ошибки больше не нуждается в пустом месте для профиля. Успешный сценарий не знает о флаге ошибки. Проверка каждого случая написана прямо, без выбора matcher через `if`.

Если завтра в сценарии ошибки понадобится проверить ещё одно последствие, я открою его `it`. Не придётся добавлять колонку, которую остальные строки заполнят прочерками, или менять общий callback ради одного исключения.

Повтор общей подготовки можно убрать в маленький helper. У нас эту работу уже делает `mockDefault`. Но действие и ожидание остаются в конкретном тесте. Иначе получится та же головоломка, только без слова `each`.

## А describe.each, forEach и test.for лучше?

`describe.each` размножает всю группу вложенных тестов. Так можно прогонять один контракт для нескольких реализаций. Но если внутри группы приходится спрашивать «а для этой реализации вообще нужна такая проверка?», в общий набор уже попали различающиеся сценарии. Их надо пересмотреть, а не добавлять очередной флаг в таблицу. [Документация `describe.each`.](https://v4.vitest.dev/api/describe#describe-each)

У Vitest есть и [`test.for` / `it.for`](https://github.com/vitest-dev/vitest/blob/v4.0.18/docs/api/index.md#testfor). Там строка-массив передаётся одним аргументом, а вторым доступен контекст теста. Это меняет API передачи данных. Общий callback с пятью ветками от такой замены проще не станет.

С ручными циклами важно различать две вещи. Цикл, который вызывает `it(...)` для каждой строки, создаёт отдельные тесты. Цикл **внутри одного `it`**, в котором перебирают данные и вызывают обычный `expect`, оставляет один тест: первая упавшая проверка прервёт его тело, и до следующих итераций выполнение не дойдёт.

Просто переписать `.each` в `forEach` — слабое улучшение. Данные и общее тело останутся на разных местах, а название генератора поменяется. Я хочу вернуть сценарию самостоятельность, а не подобрать другой способ его спрятать.

## Когда таблицу можно оставить

У таблицы есть понятная работа: проверить одну и ту же операцию на нескольких наборах входных данных. Например, нормализация нескольких вариантов пробелов. Действие одинаковое, ожидание устроено одинаково, у каждой строки понятное имя. Ни специальных моков, ни переключения между ошибкой и результатом.

Такой пример не становится нечитаемым только от наличия `.each`. Моё возражение начинается там, где ради экономии строк в таблицу запихивают разные способы подготовки и разные проверки. Особенно когда к строкам прикручивают флаги и функции, которые надо открыть отдельно.

В ESLint-плагинах даже есть [`vitest/prefer-each`](https://github.com/vitest-dev/eslint-plugin-vitest/blob/main/docs/rules/prefer-each.md) и [`jest/prefer-each`](https://github.com/jest-community/eslint-plugin-jest/blob/main/docs/rules/prefer-each.md). Эти правила предлагают `.each` вместо ручной генерации тестов циклом. Они не требуют упаковывать любые похожие `it` в таблицу и не оценивают, насколько внятно получилось описать сценарий.

## Как распутать уже написанное

Я бы начал с таблицы, которая уже мешает чинить тест или добавлять нужный случай. Переписывать весь репозиторий за один заход незачем.

1. Прогнать текущие проверки и выписать сценарии, которые таблица создаёт. Не потерять отрицательные и пограничные случаи при переносе.
2. Вытащить один сложный случай в отдельный `it`. Перенести именно его данные, подготовку и ожидание.
3. Убрать из этого теста условия, которые обслуживали соседние строки. Ожидаемую ошибку оставить ожидаемой ошибкой, успешный ответ — успешным ответом.
4. Удалить перенесённую строку из таблицы, затем прогнать весь файл. Проверить и имена сценариев, и их результаты; один зелёный тест не подтверждает, что при переносе ничего не забыли.
5. После переноса остальных случаев посмотреть, что действительно повторяется. В helper вынести обычную подготовку, а не ещё один универсальный движок сценариев.

## Запустить пример

[Полный пример](examples/each-readability) содержит оба варианта: таблицу и три явных сценария. Vitest закреплён на **4.0.18**, нужен Node.js **22.12+ в ветке 22** или **24**.

```bash
git clone --branch docs/each-test-readability https://github.com/bad4iz/unit-test-article.git
cd unit-test-article/examples/each-readability
npm ci
npm test
```

На Node.js **22.16.0** прошли все **шесть тестов**: по три случая в каждом варианте. Запуск по имени вместе с путём к файлу выбрал одну строку таблицы.

Это сравнение читаемости. Приложение, данные и ожидаемые результаты в двух вариантах одинаковые; замеров производительности здесь нет.

Мне не жалко повторить три понятные строки. Жалко открывать упавший тест и сначала изучать язык, на котором его решили описать.
